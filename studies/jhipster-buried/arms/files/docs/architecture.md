# Architecture

The application follows the standard JHipster layering.
Each layer lives in its own package under `io.github.jhipster.sample`.

## Layers

- `web.rest`: REST resources (controllers). They translate HTTP to service calls and back, and nothing else.
- `service`: business logic and transactions. Services are the only place where several repositories are combined.
- `service.dto` and `service.mapper`: data transfer objects and MapStruct mappers between entities and DTOs.
- `repository`: Spring Data JPA repositories. No business logic, only queries.
- `domain`: JPA entities. Entities hold state and simple invariants, not workflows.
- `security`: authentication, authorities and helpers around the security context.
- `config`: Spring configuration. Beans that are needed across layers are declared here.
- `aop`: cross-cutting aspects, currently only logging.
- `management`: actuator extensions.

## Dependency rules

- `web` may depend on `service`, `security` and, for simple CRUD resources generated by JHipster, `repository`.
- `service` may depend on `repository`, `domain`, `security` and `config`.
- `repository` depends only on `domain`.
- `domain` depends on nothing in the application.
- `config` must not depend on `web`.
- These rules are checked by `TechnicalStructureTest` (ArchUnit); a failing test means the dependency is wrong, not the test.

## Generated code

- JHipster generated most of the CRUD code from the JDL in `.jhipster/`.
- When you change an entity, prefer regenerating with `jhipster entity <Name>` over hand-editing all layers.
- Hand-written changes in generated files must be marked with a short comment so a later regeneration can be merged.
- Do not edit files under `target/` or `node_modules/`.

## Configuration

- Application properties live in `src/main/resources/config/application*.yml`.
- Custom properties go into `ApplicationProperties` with the `application.` prefix, never as loose `@Value` strings.
- Profile-specific behaviour uses the `dev`, `prod` and `test` profiles; do not invent new profiles for a single feature.
- Feature switches are properties with a safe default, documented in `application.yml`.

## Cross-cutting concerns

- Logging goes through SLF4J; the logging aspect logs entry and exit in the `dev` profile only.
- Caching uses Ehcache via the Hibernate second-level cache and Spring's cache abstraction; see [persistence](persistence.md).
- Asynchronous work uses `@Async` with the executor from `AsyncConfiguration`; never create threads by hand.
- Scheduled jobs use `@Scheduled` with a cron expression from the application properties.
- Mail goes through `MailService` and Thymeleaf templates in `src/main/resources/templates/mail`.

## When in doubt

- Look for an existing example of the same kind of change and follow it.
- Keep new classes in the package of the layer they belong to; do not create new top-level packages.
- A new top-level package or a new layer needs an architecture decision first.
