# Ablation: what the pointer and the feedback loop each do

Confirmatory runs under [analysis-plan.md](analysis-plan.md): 144 runs on jhipster-buried, fastapi-crud-status and bulletproof-notify-querykey, Sonnet and Haiku, 8 runs per arm, model and study.
The full tables are generated by `bench.mjs compare`: [ablation-loop.md](ablation-loop.md) (H1) and [ablation-pointer.md](ablation-pointer.md) (H2).

## Results against the plan

| Hypothesis | Result | Verdict |
|---|---|---|
| H1: without the loop (`pointer_only`), more runs break a rule | 8/48 against 0/48; exact CMH p = 0.001 | supported |
| H2: without the pointer (`rule_only`), runs cost more | +13% (95% interval +3% to +24%) | supported |
| H3: verify outcome (production code passes the original suite) | `pointer_only` 47/48, `rule_only` 48/48, `rules_control` 47/48 | no difference |

## What the results mean

- All 8 breaks without the loop are the mechanical status-code rule on FastAPI task T2.
  That rule has no pointer line, so in `pointer_only` it is stated nowhere, and the agent copies `status_code=404` from the existing code in every T2 run of both models.
- The three design-shaping rules, each with its pointer line, were broken 0 of 48 times in production code with the pointer alone.
  So the loop's measured value is enforcing rules that have no prose, not backing up a pointer that is ignored.
  This corrects F1 of the exploratory report ("the pointer alone is not the guarantee"): the in-session loop catches it rested on were intermediate edits, which the agent also fixes by itself when there is no loop.
- Without the pointer, the loop catches the design-shaping rule 115 times against 45 with it, and runs cost 13% more: the pointer lets the agent write the right shape first, and the loop alone gets there through rework.
  The cost difference is clearest on jhipster Sonnet (+21%) and bulletproof Sonnet (+34%); FastAPI shows none (+2%).
- Without the loop, runs cost 12% more (interval +0% to +24%), from the review fix the 8 broken runs needed.
- Every run of all three arms ended with no rule broken.
- The 2 production failures (one `pointer_only`, one `rules_control`) are the same Haiku compile error in `OperationResource.java`, unrelated to the rules.

## Limits

- One mechanical rule without prose carries H1; a study where a mechanical rule appears in prose but not in a pointer would test the loop against stated prose.
- Several test steps passed only on a retry (marked flaky in each study's summary); retries are recorded and none changed a verdict.
